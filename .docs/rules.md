## Обязательные правила

### 1. Язык коммуникации и кода

**Правило:** Разделяем языки по контекстам использования.

**Применение:**
- **Общение с командой:** только русский язык
- **Код и комментарии в коде:** только английский язык
- **Документация:** русский язык (за исключением технических терминов)
- **UI для пользователей:** интернационализация (en/ru)

**Примеры:**

 **Правильно:**
```typescript
// Calculate total price with tax
function calculateTotal(price: number, taxRate: number): number {
  return price * (1 + taxRate);
}
```

 **Неправильно:**
```typescript
// Вычислить общую цену с налогом
function calculateTotal(цена: number, ставкаНалога: number): number {
  return цена * (1 + ставкаНалога);
}
```

**Обоснование:** Английский — международный стандарт для кода. Русский — для прозрачной коммуникации в команде. Смешивание языков в одном контексте создаёт путаницу.

---

### 2. Использование эмодзи и иконок

**Правило:** Эмодзи и иконки запрещены в любом виде и везде в проекте.

**Где запрещено:**
-  Исходный код (TypeScript, JavaScript, SQL и т.д.)
-  Комментарии в коде
-  Commit messages
-  Техническая документация (манифест, stages, API docs)
-  Логи и error messages
-  Markdown документация
-  Презентации и маркетинговые материалы
-  Любые текстовые файлы проекта

**Примеры:**

 **Правильно:**
```typescript
logger.error('Failed to upload file', { filename, error });
```

 **Неправильно:**
```typescript
logger.error('Failed to upload file', { filename, error }); // Даже в комментариях запрещено
```

**Обоснование:** Эмодзи нарушают чистоту кода, создают проблемы с encoding, усложняют чтение и не добавляют технической ценности. Проект придерживается строгого подхода без визуальных украшений в текстовых файлах.

### 3. Чистота и комментирование кода

**Правило:** Код должен быть чистым, самодокументируемым и комментироваться только в ключевых местах.

**Что значит "чистый код":**
- Понятные названия переменных и функций
- Короткие функции (одна ответственность)
- Избегание магических чисел и строк
- Консистентное форматирование (через Prettier)
- Type-safety (TypeScript strict mode)

**Когда комментировать:**
- Сложная бизнес-логика, требующая объяснения
- Неочевидные оптимизации или workaround'ы
- Алгоритмы с нетривиальной логикой
- Public API и экспортируемые функции (JSDoc)

**Когда не комментировать:**
- Очевидный код (хорошие имена сами себя объясняют)
- Повторение того, что код уже говорит

**Примеры:**

 **Правильно:**
```typescript
// Generate slug with uniqueness check and retry logic
// If collision occurs, append timestamp to ensure uniqueness
async function generateUniqueSlug(baseText: string): Promise<string> {
  const baseSlug = slugify(baseText);
  const exists = await checkSlugExists(baseSlug);
  
  if (!exists) return baseSlug;
  
  return `${baseSlug}-${Date.now()}`;
}
```

 **Неправильно:**
```typescript
// This function generates a slug
function generateSlug(text: string): string {
  // Convert to lowercase
  const lower = text.toLowerCase();
  // Replace spaces with dashes
  const dashed = lower.replace(/ /g, '-');
  // Return result
  return dashed;
}
```

**Обоснование:** Избыточные комментарии — это технический долг (устаревают, противоречат коду). Хороший код читается как проза без комментариев.

### 4. Контекстуальная разработка

**Правило:** При добавлении новой функциональности учитывать существующий контекст проекта.

**Что проверять перед изменениями:**
1. **Архитектурная совместимость:** новая фича вписывается в микросервисную архитектуру?
2. **Структурный позвоночник:** не ломает ли изменение базовые сущности (Account → Persona → Project)?
3. **Обратная совместимость:** не сломается ли существующий функционал?
4. **Database schema:** требует ли изменение migration, backward-compatible ли оно?
5. **API contracts:** не breaking change ли это для существующих клиентов?

**Процесс:**
```
1. Изучить связанный код
   ↓
2. Понять существующие паттерны
   ↓
3. Спроектировать изменение
   ↓
4. Проверить на breaking changes
   ↓
5. Написать тесты
   ↓
6. Реализовать
   ↓
7. Обновить документацию
```

**Обоснование:** Новый код должен органично встраиваться в существующую систему, а не создавать "заплатки" и технический долг.

### 5. Уточнение при неопределённости

**Правило:** При возникновении непонимания или неоднозначности — всегда уточнять у автора задачи.

**Когда уточнять:**
- Требования неоднозначны или противоречивы
- Не хватает технических деталей для реализации
- Несколько альтернативных решений с разными trade-off'ами
- Изменение может повлиять на существующую функциональность
- Неясен приоритет между конфликтующими требованиями

**Как уточнять:**
- Сформулировать конкретный вопрос
- Предложить 2-3 варианта решения с плюсами/минусами
- Указать, на что повлияет выбор решения

**Примеры вопросов:**

 **Правильно:**
> "Для placeholder reordering есть два подхода:
> 1. Оптимистичный UI (instant feedback) + eventual consistency
> 2. Pessimistic locking (wait for server confirmation)
>
> Подход 1 быстрее для пользователя, но сложнее в реализации.
> Подход 2 проще, но медленнее UX. Какой выбрать?"

 **Неправильно:**
> "Как делать reordering?"

**Обоснование:** Лучше потратить 5 минут на уточнение, чем день на переделку неправильно понятой задачи.

## Руководящие принципы

Проект следует принципам STANDART — универсальной методологии для создания предсказуемых, прозрачных и безопасных систем.

ПРЕАМБУЛА / ОБЩАЯ НОТА ДЛЯ STANDART

**Определение**

STANDART — это методологический каркас, предназначенный для того, чтобы любая система (проект, процесс, продукт, исследование) развивалась предсказуемо, прозрачно и безопасно.

**Суть подхода**

STANDART предполагает, что работа над системой должна быть:

понятной (структура),

обратимой (недеструктивность),

доступной для анализа (прозрачность),

разбитой на независимые части (модульность),

недвусмысленной (дефиниции),

оптимизированной (автоматизация),

поступательной (контрольные этапы),

проверяемой (check-in/out).

**Главная идея**

Система должна развиваться так, будто её можно разобрать, пересобрать, откатить, расширить или адаптировать без разрушения целого и без потери состояния.

Эта нота — «философская верхушка».

Теперь принципы, уже под неё выровненные.

STANDART — универсальные принципы

Формат тот же: определение → объяснение → пример (абстрактный, не привязанный к проекту).

---

### **S — Structural Backbone**

**Определение**

Система должна иметь чёткий, явный и предсказуемый структурный каркас, в который встроены все её элементы.

**Объяснение**

Пользователь, разработчик или аналитик всегда должен понимать,
где что лежит, как устроено, как соотносится и куда двигаться.

**Абстрактный пример**

У документа есть оглавление и логичная иерархия.

Архитектура кода разбита на слои.

В базе данных структура отражает реальные сущности.

---

### **T — Trace-Reversible / Non-Destructive Workflow**

**Определение**

Рабочий процесс должен сохранять возможность возврата на любой предыдущий шаг без потери информации.

**Суть**

Недеструктивность — это не просто «не ломать»,
а не уничтожать предыдущие состояния системы.

Ниже — правильные ассоциации:

Photoshop: объединение слоёв → деструктивно

Nuke / Blender nodes: всё хранится в узлах → недеструктивно

Git: любой коммит можно чекнуть → недеструктивно

Выборка данных в SQL без перезаписи → недеструктивно

**Пример**

Вместо «экспортировать и затирать файл» — создавать новые версии.

Вместо «переписывать слой» — работать через историю изменений.

Вместо «ломать таблицу» — мигрировать с сохранением старой схемы.

---

### **A — Absolute Transparency**

**Определение**

Система должна позволять в любой момент увидеть текущее состояние, историю решений, статус задач и логику изменений.

**Суть**

Никаких чёрных ящиков.
Любой участник может понять почему и как было сделано то или иное действие.

**Пример**

Логи, отчёты, открытые документы.

История правок в Google Docs или Git.

Взгляд на текущий pipeline в CI/CD.

---

### **N — Non-Monolithic Modularity**

**Определение**

Система должна состоять из независимых модулей, которые можно заменять, обновлять или тестировать изолированно.

**Суть**

Модульность — это переносимость, масштабируемость и простота развития.

**Пример**

Микросервисы вместо гигантского бэкенда.

Документ разбит на главы, а не 200 страниц слитного текста.

Процессы описаны отдельными процедурами, а не «в одном файле».

---

### **D — Defined Terms First**

**Определение**

Каждый новый термин, концепт или конструкция должны быть определены до того, как используются.

**Суть**

Определение → использование → выводы
а не наоборот.

**Пример**

Перед использованием слова «граф» дать определение,
перед использованием понятия «модуль» — объяснить, что такое модуль.

---

### **A — Automate Everything**

**Определение**

Любое повторяемое действие должно быть автоматизировано, если это сокращает количество ошибок и повышает эффективность.

**Суть**

Руками — только уникальное.
Рутинное — автоматизация.

**Пример**

Шаблоны документов.

Скрипты для сборки.

Пайплайны проверки данных.

Автогенерация отчётов, диаграмм, конфигураций.

---

### **R — Roadmap Checkpoints**

**Определение**

Работа над системой разделяется на чёткие этапы, между которыми располагаются контрольные точки — места проверки, фиксации и возможного отката.

**Суть**

Это — этапы прогресса, формирующие дерево состояния системы.

**Пример**

Этап 1: Аналитика → КТ1: проверка требованиями

Этап 2: Дизайн → КТ2: проверка макетов

Этап 3: Разработка → КТ3: ревизия архитектуры

---

### **T — Two-Way Verification**

**Определение**

Каждый входящий артефакт проходит проверку на входе (check-in), а каждый выходящий — на соответствие ожиданиям (check-out).

**Суть**

Двойной контроль качества и соответствия.

**Пример**

Check-in: подтверждение требований.

Check-out: проверка результата тестами и ревью.

Итоговая формула STANDART (универсальная)
S — Structural Backbone
T — Trace-Reversible Non-Destructive Workflow
A — Absolute Transparency
N — Non-Monolithic Modularity
D — Defined Terms First
A — Automate Everything
R — Roadmap Checkpoints
T — Two-Way Verification

## Объектно-ориентированное программирование и SOLID принципы

**Правило:** При разработке классов и модулей обязательно следовать принципам SOLID.

**SOLID принципы:**

**S — Single Responsibility Principle (Принцип единственной ответственности)**
- Каждый класс должен иметь только одну причину для изменения
- Класс должен решать только одну задачу

**O — Open-Closed Principle (Принцип открытости-закрытости)**
- Классы должны быть открыты для расширения, но закрыты для модификации
- Новое поведение добавляется через наследование или композицию

**L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
- Объекты подкласса должны быть взаимозаменяемы с объектами базового класса
- Наследник не должен нарушать контракт родителя

**I — Interface Segregation Principle (Принцип разделения интерфейсов)**
- Клиенты не должны зависеть от интерфейсов, которые они не используют
- Разделять большие интерфейсы на меньшие, специфические

**D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
- Модули верхнего уровня не должны зависеть от модулей нижнего уровня
- Оба должны зависеть от абстракций
- Абстракции не должны зависеть от деталей, детали должны зависеть от абстракций

**Применение в проекте:**
- Все классы сервисов должны следовать SRP
- Использовать dependency injection вместо прямых зависимостей
- Создавать интерфейсы для ключевых контрактов
- Тестировать каждый принцип при code review

**Примеры нарушения SOLID:**
```typescript
//  Нарушение SRP - класс делает слишком много
class UserService {
  createUser() {}
  sendEmail() {}      // Не относится к управлению пользователями
  generateReport() {} // Не относится к управлению пользователями
}

//  Правильно - разделение ответственности
class UserService {
  createUser() {}
}

class EmailService {
  sendEmail() {}
}

class ReportService {
  generateReport() {}
}
```

## Рабочая среда

### Локальная разработка

**Операционная система:** Windows 11
**Ограничения:**
-  Docker недоступен локально
-  WSL не установлен
-  Git доступен
-  Node.js + pnpm доступны
-  VSCode как основная IDE

**Следствия:**
- Тестирование Docker локально невозможно
- Development через native Node.js процессы
- Compose profiles тестируются только на VPS

---

### Удалённый сервер (VPS)

**Операционная система:** Ubuntu Server
**Доступная инфраструктура:**
-  Docker + Docker Compose
-  PostgreSQL
-  Redis  
-  Nginx (если нужен)
-  SSL certificates (Let's Encrypt)

**Назначение:**
- Deploy и тестирование
- Integration tests
- Performance benchmarks
- Stage environment

**Доступ:**
- SSH key authentication
- Управление через SSH
- Логи через `docker compose logs`

Сonstitution — это живой документ. Он описывает текущие правила работы над проектом и может дополняться по мере роста. Все изменения в Codex должны проходить review и согласовываться с автором проекта.

При возникновении ситуаций, не покрытых этим документом, руководствуйтесь здравым смыслом и задавайте вопросы команде.
